# Controlled migration

Generation is read-only against the cluster. Every generated manifest is accompanied by a review plan containing the original DC snapshot, intended replicas, semantics, warnings, blockers and recovery instructions. Offline/generation plans have incomplete dependent-resource inventory and cannot execute.

Create a live plan with `--mode plan --projects example --context TEST_CONTEXT`. This inventories namespace Services, HPAs and controllers without changing them. A later stage revalidates the source UID/resource version, source spec, dependencies and controller overlap. Permissions for optional planning are separate from ordinary generation. Review the plan, pod labels, selected context, dependent resources and warnings before application.

`--mode dry-run --plan-file PATH --context TEST_CONTEXT` submits only a paused, zero-replica destination for server dry run. `--mode stage` performs the same dry run then creates that destination. Image triggers are removed during staging. Existing destinations require explicit source and plan ownership and must still match the admitted staged spec. Foreign objects, changed plans, active destinations and conflicting creates are never overwritten. A journal records creation intent before mutation; a safe rerun discovers a previously created owned destination. The plan uses a local exclusive lock; after process death, inspect the process/cluster/journal before removing a stale `.lock` file.

The old `--apply-changes` flag now aliases staging and requires `--plan-file`; it cannot start a second active workload. Staging does not retire the DC or move traffic. Unsupported semantics produce manual diagnostics and prevent staging. Admission changes to protected identity, selector, images, pod labels, pause or replica count fail the operation. Other defaults/admission changes are recorded for review.

Use private storage for plans: snapshots can contain environment values. Keep the DC for recovery. Cutover and recovery procedures must always stop and verify the destination before restarting an exclusive source; never delete the DC as an automatic cleanup step.

`--mode cutover --plan-file PATH --context TEST_CONTEXT --automation-quiesced` executes only a staged plan. The acknowledgement means external GitOps, operators, scheduled scalers, other migration invocations and application jobs have been paused or coordinated. Use one operator/process for a migration; the local lock is not a distributed lease. The plan's source version is checked strictly, including status-only resource-version changes; inspect stale plans before replanning. A new plan cannot silently adopt a staged object with a different plan digest.

In the default **exclusive** procedure, the tool snapshots and temporarily removes source HPAs using UID/version preconditions, disables DC image/config triggers, leaves replica reconciliation unpaused while scaling the DC to zero, and waits for its RCs and pods to stop. Only then does it pause the retired DC. It then unpauses/scales the destination, verifies its observed generation and available replicas, checks Service endpoint references, and calls the plan's health URL. The DC remains at zero with triggers disabled for recovery. HPAs are recreated to target the Deployment after it is ready. Service selectors are retained.

For **overlap**, choose `--cutover-mode overlap --overlap-justification 'REASON'` when planning. Only use this for a workload whose application semantics allow parallel copies. The tool blocks overlap with volumes, host namespaces and host ports. It quiesces source triggers and autoscaling, activates and verifies the destination while source pods still run, then retires the source and retargets HPAs. A singleton worker must use exclusive mode even if it has no volumes. A paused source requires a manual activation design and cannot enter automatic cutover.

A nonzero workload requires a credential-free `--health-url https://APPLICATION/health` recorded during planning. Queries, fragments, URL credentials and redirects are rejected. HTTP is available for isolated test networks. A successful response must be 2xx. Health failures are retried within the readiness timeout to allow Route/backend convergence; a persistent failure retains the last health error and cannot count as ready or restored. A zero-replica workload does not require endpoints or an application-health request. Readiness/retirement have `--readiness-timeout`; all requests share the operation context and retain per-request deadlines.

A failed or interrupted cutover is not automatically declared recovered. Run `--mode rollback --plan-file PATH --context TEST_CONTEXT` after inspecting the journal. Recovery removes migrated HPAs, stops/pauses the owned destination, disables its image triggers, and waits for destination pods to disappear before restoring the source spec and HPA targets. It preserves the DC, original replica count and dependent snapshots. It verifies restored source availability and health before recording recovery. If access is lost, source/destination ownership changes, an unrelated spec changes or a journal cannot be saved, stop and inspect the cluster; the tool returns failure and never claims recovery. Do not restart an exclusive source until destination termination is verified. A stale local lock may need manual removal after process/cluster inspection.

Source updates during cutover and rollback retry definite resource-version conflicts at most **five total attempts per transition**. The four waits are 100, 200, 400 and 800 milliseconds, bounded by cancellation and the operation deadline. Every attempt reads the source again, verifies its original UID and non-deleting state, compares its complete spec with the spec pinned at the start of that transition, and repeats server dry run before a real update. Status or metadata churn can therefore be tolerated, but any spec change stops the retry, even if it resembles another valid migration state. The initial staged-plan freshness check remains strict.

Retries apply only to confirmed conflict responses from source dry-run/update requests. Lost responses, EOFs, timeouts, other API errors and mismatched persisted admission remain failures on the explicit recovery path. Earlier migration steps may already have changed triggers, replicas or HPAs. Exhausted conflicts retain the journal and require inspection and explicit rollback; the tool does not restart the whole cutover automatically. Other resource mutations retain their existing recovery behavior.

HPA recreation is explicit and temporarily interrupts autoscaling; owner-managed or finalizer-bearing HPAs require manual coordination. No source manifest or Service is deleted. Resource updates use optimistic concurrency and server dry run; webhook differences between dry run and persistence are failures requiring inspection. SCC pod admission and image-controller behavior remain actual-cluster qualification requirements.

OpenShift 4.14's [DC controller source](https://github.com/openshift/openshift-controller-manager/blob/release-4.14/pkg/apps/deploymentconfig/deploymentconfig_controller.go) returns before replica reconciliation when `spec.paused` is true. Trigger removal prevents automatic new rollouts while replicas reconcile; pausing must follow confirmed retirement. Pending/running source deployers require completion or explicit cancellation before planning. This source check supplements, and does not replace, actual-cluster qualification.

Before the first cutover mutation, the staged target is checked again for its exact UID, ownership, admitted spec and zero-replica pause state. Changed or deleting targets fail before source retirement. Orphaned/foreign migration ReplicaSets block staging; a matching label alone cannot establish ownership. Deleting HPAs cannot count as restored. If a destination Deployment disappears, recovery still waits for its labelled ReplicaSets and pods to stop before restoring the source.

An automatic ImageChange trigger must have a resolved `lastTriggeredImage` before live migration. For `oc new-app --as-deployment-config --binary` apps, finish the initial build/import and wait for the DC image controller, then generate a fresh live plan. Read-only conversion can still produce review artifacts while the image is pending. Live planning/staging and cutover of older saved plans reject unresolved triggers; explicit recovery remains available.

## Constraints before source retirement

A paused, zero-replica Deployment dry run does not prove that its Pods can start. After staging, run:

```sh
openshift-dc-converter --mode preflight --plan-file ./review/example/web.plan.json \
  --context TEST_CONTEXT --json-report ./preflight.json --report-path ''
```

This performs API dry runs and reads without persisting workload resources. It writes a timestamped `constraints` assessment to the JSON report and plan progress, including desired/capacity replica counts, per-check results, blockers and warnings. Success means these checks passed; it never reports the workload ready or applied. Cutover **always repeats** the assessment immediately before its first HPA/source mutation, including for previously staged plans; a saved successful assessment cannot authorize later retirement.

The gate checks active Deployment and source-retirement admission, HPA deletion/recreation admission, representative ReplicaSet/Pod admission, LimitRanges, and SCC authorization for the actual workload service-account identity and groups. The SCC review supplies Pod defaults while preserving destination policy labels/annotations. Both the SCC review's defaulted Pod spec and the raw Pod admission response are validated against the baseline field catalog before typed conversion. Post-baseline fields, including resource budgets, image volumes and newer security-context policies, block automatic cutover instead of being discarded or bypassing placement assessment. Removed/rewritten required labels also block execution. HPA dry-run deletion checks its UID and planned spec while tolerating status-only resource-version churn; the later real deletion retains UID/version preconditions. It checks namespace ResourceQuota and shared ClusterResourceQuota usage through the namespace's AppliedClusterResourceQuota projection. Per-Pod dry run is combined with cumulative requests/limits and object counts, because one accepted Pod does not prove the full replica set fits. Quota accounting that has not synchronized, unavailable APIs and denied inventory/validation permissions block execution.

Capacity checks retain **all current source consumption** and require room for the destination replica count **plus its configured rolling surge**. They never assume source termination will free enough quota or capacity. This conservative policy can reject an exclusive migration that would fit after downtime; request temporary headroom or use a reviewed manual maintenance procedure. Diagnostics identify the quota/resource and used/additional/hard amounts where applicable. Namespace quotas, shared quotas, and node capacity are separate checks; a namespace with free quota can still lack schedulable nodes.

Node checks use current allocatable resources and all nonterminal bound Pods, including overhead, init/sidecar requirements, in-place allocations and newer observed Pod budgets without emitting newer fields in baseline manifests. They evaluate Ready/schedulable/pressure state, selectors, required node affinity, untolerated taints, host-port conflicts, pod slots, compute/extended requests and mounted PV node affinity. Missing/unbound/deleting claims block migration. Required inter-Pod affinity, hard topology spread, custom schedulers, host namespaces, dynamic claims and other placement rules this estimator cannot safely evaluate require manual review. Nonzero checks need the additional [read and dry-run permissions](rbac.md); zero-replica cutover does not assess Pod startup or need node inventory.

PV zone/region labels are independent scheduler constraints, even when `spec.nodeAffinity` is absent or matches. A mounted PV carrying `failure-domain.beta.kubernetes.io/zone`, `failure-domain.beta.kubernetes.io/region`, `topology.kubernetes.io/zone` or `topology.kubernetes.io/region` therefore requires manual scheduling review before source retirement. The tool does not simulate the cross-version label fallback or multi-zone value rules. It does not remove these labels or rewrite the PV. Unlabelled CSI PVs with assessed node affinity remain usable; successful preflight still does not reserve CSI attachment slots or prove driver mounts.

PodDisruptionBudgets are checked against current source Pods before retirement, because controller scale-down bypasses eviction protection. Exclusive cutover is blocked when it would remove more selected Pods than the current synchronized budget allows; overlap can preserve an absolute `minAvailable` budget when verified destination replacements also belong to it. Controller-relative percentage/`maxUnavailable` budgets require a reviewed procedure during overlap. Kubernetes explains why [direct workload deletion/updates are not protected by the Eviction API](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/).

A NetworkPolicy workload or peer Pod selector that selects current source Pods and the destination differently blocks retirement. The comparison uses running source labels, including DC controller-added `deployment` labels, rather than assuming the source template contains every runtime label. Unchanged workload selection is recorded with a warning that peer selectors, external rules and actual target traffic still need runtime verification. A preflight refusal leaves the original HPA, source replicas/triggers/spec and destination paused at zero, with journal phase `staged`. Fix the constraint and rerun if the plan remains fresh. Failures after actual cutover mutations still require explicit recovery.

The same protection covers optional cluster AdminNetworkPolicy and BaselineAdminNetworkPolicy subject and ingress/egress peer Pod selectors. Discovery checks which policy API is served; absent APIs are skipped, while denied inventory and unassessed versions/resources/fields require manual review. The tool uses target Namespace labels and actual source Pod labels, including runtime labels. It checks policies across all namespaces because another workload's peer rules can reference this application. Matching Pod selection is not a complete network-policy evaluation: rule priority, ports, node/IP/domain reachability and actual connectivity remain runtime checks. Policy reads occur before source/HPA mutation; explicit recovery bypasses the new gate.

See [OpenShift admin policy semantics](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/network_security/admin-network-policy) and the [upstream policy API schema](https://network-policy-api.sigs.k8s.io/reference/spec/). The converter assesses the discovered `v1alpha1` selection fields; other policy API versions require manual review.

Namespace and admin policy Pod selectors that depend on `pod-template-hash` require manual review. The Deployment controller adds this label after Pod dry run, and its future value is not part of the staged template. Treating it as absent would miss a policy change; the tool does not guess a controller hash across Kubernetes versions.

Capacity covers the reviewed replica count and rolling surge; it does not reserve capacity for future HPA scaling. Preflight is **a point-in-time assessment, not a reservation or a guarantee of startup**. Policies, quotas and allocations can change after it; image pulls, application readiness, controller-user/generated-name-specific webhooks, custom scheduler plugins, CSI attachment/mounting and external dependencies can still fail. These limits are shown before retirement. Keep runtime readiness/health checks and a recovery plan. No duplicate test Pod is started to guess whether an exclusive worker is safe.

The distinction follows Kubernetes' [dry-run semantics](https://kubernetes.io/docs/reference/using-api/api-concepts/#dry-run), [Pod admission and quota behavior](https://kubernetes.io/docs/concepts/policy/resource-quotas/) and OpenShift's [SCC subject-review API](https://docs.redhat.com/en/documentation/openshift_container_platform/4.14/html/security_apis/podsecuritypolicysubjectreview-security-openshift-io-v1). Actual 4.14 qualification remains separate from using these baseline APIs.
